## 1. Name and purpose

ECTOS OMNIGATE is the universal ECTOS control methodology for turning authoritative input sources plus a defined terminal objective into one fully mapped, dependency-closed, evidence-bound, qualification-ready execution chain before ordinary construction or execution begins.

OMNIGATE applies to every significant ECTOS intake and to application creation beyond ECTOS whenever the same governed method is selected.

It is not limited to packages or qualification. It applies to blocks, components, tools, validators, qualifiers, executables, applications, pipelines, Factory components, Cloud integrations, handoff objects, and complete systems.

## 2. Core invariant

INPUTS=AUTHORITATIVE_SOURCE_SET + TERMINAL_EXPECTED_RESULT

REQUIRED_TRANSFORMATION=
AUTHORITATIVE SOURCES
-> COMPLETE BACKWARD DEPENDENCY MAP
-> COMPLETE FORWARD TARGET CHAIN
-> PRE-BUILD ACCEPTANCE MATRIX

-> ONE-SHOT EXECUTION ORDER

Execution must not be used to discover dependencies, interfaces, runtimes, tools, evidence requirements, authority boundaries, currentness requirements, or downstream conditions that could have been determined safely beforehand.

## 3. Mandatory backward pass

Start from the exact terminal expected result and recursively ask what physical states, objects, identities, interfaces, tools, runtimes, evidence, authorities, and dependencies are required to make that result admissible.

Continue until authoritative sources are reached.

For every node and edge record:
- producer
- consumer
- input identity
- output identity
- version/currentness
- dependencies and transitive dependencies
- interface
- path
- runtime and OS
- configuration
- authentication and authorization
- evidence
- negative controls
- fail-closed conditions
- rollback
- downstream acceptance requirements

## 4. Mandatory forward closure pass

From the authoritative sources, prove the complete route to the terminal result:

SOURCE
-> BUILD
-> STATIC ASSURANCE
-> NATIVE RUNTIME ASSURANCE
-> MATERIALIZATION / PACKAGE
-> ARTIFACT IDENTITY
-> EXECUTION
-> EVIDENCE
-> INDEPENDENT QUALIFICATION
-> ADMISSION
-> INTEGRATION
-> FINAL CONSUMER
-> POST-INTEGRATION PROOF

No unmapped edge may be deferred to live execution.

## 5. Tool-target fitness

Every tool used to create, validate, qualify, package, inspect, transfer, or admit another object must itself be proven fit for the exact target before it may contribute acceptance evidence.

Required review includes tool identity, package closure, version, manifest, dependency graph, runtime, OS, interfaces, required gates, negative controls, known historical failure families, reconstructibility, and qualification state.

UNPROVEN_TOOL_TARGET_FIT=BLOCK

## 6. Artifact identity and evidence chain

Before materialization define the exact artifact identity contract: member set, member count, paths, byte hashes, size, encoding, newline policy, ordering, timestamps, manifests, dependency graph, content identity, archive identity, determinism and canonical filename.

Every evidence object must identify producer, consumer, exact input bindings, output bindings, SHA256 bindings, pass contract, fail contract and currentness requirement.

Circular identities are prohibited.

## 7. Authority separation

Producer != Execution Operator != Independent Qualifier != Main Admission Authority != Factory != Integration Operator != Final Consumer.

BUILD != QUALIFICATION
QUALIFICATION != ACCEPTANCE
ACCEPTANCE != HANDOFF
HANDOFF != DESTINATION PROOF

No role silently inherits another role's authority.

## 8. Consolidated systemic review

Continue all safe read-only analysis to the maximum physically reachable scope.

Do not return first-defect-only results when further analysis is possible.

Create one consolidated register covering every detectable product, tool, dependency, interface, runtime, qualification, evidence, currentness, integration, authority and methodology defect.

Multiple defects in the same family are remediated systemically, not serially.

## 10. One-shot execution contract

Only after preclosure is complete, produce one ordered plan in which every step declares:
- step ID
- exact input
- exact action
- exact output
- evidence produced
- pass condition
- fail condition
- next eligible step

The execution plan is a verification of already-closed assumptions, not a discovery process.

## 11. Failure contract

On failure:
STOP
NO_SILENT_RETRY
NO_LAST_ERROR_ONLY_PATCH
NO_AUTOMATIC_MICRO_SUCCESSOR

Classify whether the failure was genuinely non-pre-detectable or should have been found by OMNIGATE preclosure.

If pre-detectable:
SYSTEMIC_REVIEW_ESCAPE=YES
METHODOLOGY_DEFECT_REGISTER_UPDATE=MANDATORY

No further execution authority is eligible until the escape is systemically adjudicated.

## 13. Universal intake rule

For every new ECTOS project intake, block, package, tool, component, validator, qualifier, executable, application, pipeline, Factory component, Cloud integration or comparable governed demand:

1. receive authoritative sources;
2. define the terminal result;
3. run OMNIGATE backward mapping;
4. run OMNIGATE forward closure;
5. close all safely pre-detectable dependencies and assumptions;
6. produce the consolidated defect set and pre-build matrix;
7. produce one execution order;
8. only then grant creation/execution eligibility.

## 14. Method origin

This method was crystallized from the ECTOS DEV V1 executable/ZIP systemic review after the Project Owner explicitly required Main to stop serial producer/successor ping-pong, inspect the complete chain, discover all downstream blockers in advance, and prepare the path from current sources through ZIP qualification, admission, Factory and Cloud handoff before any further execution.

The resulting method converts reactive:

EXECUTE -> DISCOVER -> FIX -> RETRY

into governed:

DEFINE TERMINAL RESULT
-> MAP COMPLETE CHAIN
-> PRECLOSE ALL DETECTABLE CONDITIONS
-> UNKNOWN_ASSUMPTION_COUNT=0
-> ONE EXECUTION PLAN
-> EXECUTE / QUALIFY / ACCEPT / INTEGRATE
-> PROVE TERMINAL RESULT

END ECTOS OMNIGATE V01
